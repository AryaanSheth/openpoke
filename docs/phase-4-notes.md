## Fixes

- `tests/conftest.py:195` (now `_openrouter_binding_modules`) — **a real, independently-verified test-harness bug, not a Phase 1 regression.** `_openrouter_binding_modules()` is `functools.cache`d and computes its module list from `import server.app`, which does **not** transitively import the agent runtimes: both `server/jobs/handlers.py::handle_chat_turn` and `server/services/gmail/importance_watcher.py::_resolve_interaction_runtime` import `agents.interaction_agent.runtime` lazily, inside a function body, specifically so the module still imports if Phase 1/2 internals move. Left alone, that module (and `agents.execution_agent.{runtime,batch_manager}`, pulled in transitively) does not exist in `sys.modules` yet when the cache is first populated (at the very first test's fixture setup) — and `@cache` never re-scans. The first test in a session that only imports those modules *mid-test-body* (by actually running a job, as `test_remind_me_tomorrow` does) ends up with `agents.interaction_agent.runtime.request_chat_completion` bound to whatever the module's own `from ...openrouter_client import request_chat_completion` captured at that moment — usually a stub, but *that test's own* stub, never refreshed or torn down for that module specifically, because it was never in the cached tuple `monkeypatch` was told to touch. The next test to reach that code path talks to the **previous test's dead stub**, which has no scripted responses left and silently returns an empty no-tool-call completion. **This is exactly what the coordinator observed** (`test_important_email_arrival` — 1 LLM call instead of 3): confirmed empirically (not merely reasoned) by instrumenting the real classify/dispatch calls and watching `handle_agent_message` return an `InteractionResult` with zero recorded calls on the *current* test's stub. Fix: eagerly import both modules inside `_openrouter_binding_modules()`, before the tuple is captured, so they are always in scope regardless of which test first reaches them. Verified: `test_behavioral.py` passes both tests together, stably, across 10+ repeated runs (isolated) after the fix; reverting the fix and rerunning reproduces the 1-vs-3-call failure exactly. **This is not a Phase 1 watcher regression** — `docs/phase-1-notes.md`'s watcher rewrite is unrelated; the bug is purely in how the test harness patches OpenRouter bindings for modules that are only ever reached via lazy imports.

## New issues

1. **The coordinator's explicit question, answered: neither (a) nor (b).** The 1-vs-3-call failure they observed was not stale-fixture drift from Phase 1's per-tenant watcher rewrite, and it was not a real regression in watcher behavior — it was the conftest.py caching bug described above, which is now fixed. The watcher's per-tenant behavior itself is correct and unrelated; I did not need to touch the fixture's expected sequence to make this pass.

2. **The bridge connection (`repositories.context.run_sync`) is real, uncontrolled state outside the test transaction — the single biggest fragility in this whole file.** Every legacy proxy store (`ConversationLog`, `AgentRoster`, `ExecutionAgentLogStore`, `TriggerStore`) commits through a *separate* Postgres connection, not `db_session`'s rolled-back transaction (`docs/phase-1-notes.md` New Issues #2, unfixed — Phase 2 removes it when the agent runtime moves into the worker). `bridge_user`'s explicit `finally`-block teardown handles the case this file creates, but it is manual bookkeeping standing in for what the harness's `db_session` rollback is supposed to guarantee for free. If a future edit to `agents/*` starts writing a new table through that bridge, nothing catches the leak until someone notices extra rows in the shared local Postgres instance. Confirmed while working: the shared DB already carries live-verification rows from Phase 1 and Phase 2's own manual testing (`phase1-alice@example.test`, `phase2-*@test.invalid`, etc.) that predate this session and are not mine to clean up — informational, not a bug, but it shows the instance is not a clean-room.

3. **`test_remind_me_tomorrow` depends on disabling summarization via a settings override** (`OPENPOKE_CONVERSATION_SUMMARY_THRESHOLD=0`), because `ConversationLog._notify_summarization` schedules an independent, detached LLM call on every conversation write, sharing this test's single `LLMStub` queue with the interaction/execution agents. With summarization on, a summarization pass can interleave mid-sequence and consume a response meant for a different agent — verified: the execution agent ended up being handed a `send_message_to_user` tool call (which it doesn't have) because the response meant for its `createTrigger` call was stolen by the summarizer. The override is legitimate (the sanctioned per-test settings seam, restored in a `finally`), but it means this fixture does **not** exercise the interaction path with summarization on. Nobody has behaviorally tested the interleaving of summarization with an in-flight tool-call sequence — worth a dedicated test if summarization's own regression coverage doesn't already cover it (plan.md's Phase 4 list doesn't call it out specifically).

4. **`test_prompt_bounds.py` exists in `tests/` as of the end of this session** (it was not there earlier in the session; Phase 2 landed it while I was working). Per the contract it is Phase 2's file — I neither created nor verified its correctness, and did not run it as part of my scoped verification (the coordinator restricted me to `tests/test_behavioral.py` only, mid-session). Its presence is not evidence it is currently green.

6b. **`test_remind_me_tomorrow`'s job-claim assertion had to be made robust to a real, observed instance of shared-DB pollution.** Mid-session, `Worker.run_once()` claimed 21 pending jobs instead of the 1 this test enqueued — leftover rows from other processes' test runs against the same local Postgres (the coordinator independently flagged this exact contention). Fixed by claiming with a large `batch`/`concurrency` (so one `run_once()` covers everything pending in a single pass) and asserting on **our own job's status** (`jobs.status == 'done'` for the specific `job_id` returned by `POST /chat/send`) rather than on the aggregate claimed-count. Residual risk, not fully closed: if any of those foreign pending jobs happen to be `chat_turn`-kind, they run through `InteractionAgentRuntime` and would consume responses from **this test's own** `llm` stub (the stub patches the process-wide binding, not a per-test-scoped one), which could corrupt the scripted sequence. In every run observed this session the foreign jobs did not visibly interfere (both tests passed repeatedly), but this was not exhaustively verified against a DB seeded with actual leftover `chat_turn` jobs — flagging rather than claiming it airtight.
